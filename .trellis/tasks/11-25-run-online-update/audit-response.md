日期：2026-11-25。对象：基线 `5f66bb4` 上尚未提交的在线更新实现。
本文补充实现理由与审计处置，可按节号引用；它是事后说明，不是事前设计锁定、
owner 逐条审批或独立复测证明。

## 1. 任务授权与流程适用性（G1、G2）

用户要求 `/run` 原生支持单独的 `--update` / `-U`，同意推进，并明确说：
“这应该是个简单任务，不需要走 paseo 流程。”本任务因此直接实施，不启用
Paseo design/review 角色循环。产品要求及验收点见 [PRD](prd.md)。

[workflow.md](../../workflow.md) 的 Planning Artifacts 允许轻量任务只保留
PRD；Phase 3.3 要求记录新的技术约定，Phase 3.4 要求相关 spec 与代码在同一
任务提交批次中同步。审计所引 Paseo 角色的设计锁定、approval hash、spec
冻结关卡不适用于本任务，不能据此认定任务必须阻塞。

接受“关键决策理由应可查”的建议，以下补齐理由和边界。用户授权的是功能和
本次工作方式；以下锁、字段和提交算法是实现者的选择，不记作用户逐条批准。
本次例外已有明确任务指令，无需据此修改全仓库工作流。

## 2. 安装进程与模块边界（G1、G3）

使用同一 Rust 可执行文件的隐藏 `--prepare-online-update` 入口，理由是复用
现有安装器及 CLI supervisor，让 curl、uv、Python 继承已有进程组 / JobObject、
超时、输出上限和回收机制。HTTP 服务协调更新，Python worker 不执行安装。

`runtime_installer` 拥有运行目录、校验、发布和恢复逻辑；`online_update`
负责排空、停止、安装、激活与回滚协调；`executor` 负责参数分流与请求租约。
`AppState` 继续定义于 `routes`，后端、supervisor 和 updater 消费这个共享
运行上下文，因此保留 `routes ↔ backend`，新增 `routes ↔ online_update`
模块互引。本任务没有拆分公共 state 模块，以免扩大改动范围。
updater 内部的执行 state 不持有 updater，避免递归所有权链。

## 3. 请求排空与取消（G1）

普通请求取得 `RwLock` 读租约并交给受跟踪的执行任务，直到进程及临时目录
清理结束才释放；更新取得写租约后停止并等待 resident workers，之后才安装。
理由是 HTTP handler 结束不等于使用旧文件的进程已经退出。租约必须覆盖实际
资源使用寿命。更新等待写租约也计入请求预算，等待超时不停止后端、不改文件。

更新不持有全局执行 semaphore permit，避免占用正在排空的请求所需的容量。
写租约阻止后续普通请求开始执行，多个更新也串行执行。停止或清理无法确认时
关闭 admission，不在进程静止状态未知时恢复文件。清理及回滚可能延长响应时间。

## 4. 配置 pin 与实际版本（G1、G4）

`RUNTIME_YTDLP_VERSION` 仍必须是具体版本，但在线更新后它代表初始版本和
选择锚点；实际选定版本记入 manifest 的 `plan.yt_dlp_version`。
`online_update_from` 记录这次选择对应的配置 pin。理由是显式更新成功后，
同配置重启或 worker/recipe 修复不应撤销这次版本选择。

例如 pin=A，显式更新到 B：保持 pin=A 重启继续使用 B；把配置改为 C，
启动选择 C。保留 libs 卷才能保留在线选择。实现以当前配置与 manifest 中的
锚点比较，不记录环境变量修改历史；再次填写相同的 A 不构成新的版本选择。

这确实改变了“配置 pin 永远等于实际版本”的旧语义，不能当作完全无行为
变化。该持久化行为已写入 PRD、README 及回归测试。接受审计要求突出说明
后果的建议；不把它重新变成本任务必须逐条审批的关卡。

## 5. 最新稳定版本的选择（G1、G4）

只有显式更新请求查询 PyPI `info.version`；接受三段数字日期版本并规范化
补零，拒绝 dev/预发布等非该格式版本。与当前版本数值比较后仅选择更新版本，
不因远端版本较旧而降级。理由是 CLI 与 resident 必须安装同一具体发行版，
不能分别跟随不同渠道。正常重启不主动查询 latest 来升级。

二进制继续使用官方 GitHub 固定版本资源及 SHA2-256SUMS 校验，Python 包
交由 uv 按具体版本安装 `yt-dlp[default]`，resident 握手验证选定版本。
这些检查保证既定来源、完整性和版本一致，不保证上游新版本没有缺陷。
主动采纳上游稳定版是本功能的实际行为；没有周期性更新或后台版本跟踪。

## 6. 发布、激活与提交（G1）

1. 排空并停止消费者后，先在 staging 准备和验证候选运行时。
2. 将 `runtime/` 改名为 `update-backup/`，保留完整旧树，再发布候选。
3. 启动选定后端；resident 必须完成 worker 握手。
4. `finish_online_update` 将 backup 改名为 `update-retired-<pid>`，完成
   提交所需的目录同步，再清理 retired。同步失败尝试恢复 backup 并报告错误。
5. 提交前失败则恢复 backup 并重新启动旧后端；恢复或重启失败关闭 admission。
   启动时先恢复遗留 backup，再读取在线版本选择。

保留旧树是为了支持激活失败回滚；删除前先改名是为了让删除中断后的残缺目录
不会成为下次启动的回滚源。提交后清理失败会记录告警并可能留下 retired 目录，
不提供历史版本管理。已验证的同版本运行时可直接复用，不建立 backup。

提交点与客户端收到 HTTP 响应不是原子操作：提交之后响应丢失，版本仍可能
已经更新。这里不承诺断电持久性、跨实例共用 libs、跨启动 staging 清扫或
更新期间持续执行请求。已有测试及其证据边界见 [progress.md](progress.md)。
